## Server code map

- `src/repo/*`: the only code that queries user data. `createRepos(db, userId)` returns repos where every query is filtered by `userId` and excludes tombstones; every write runs in a transaction with `nextRev()` (per-user counter on the user row). Route handlers must go through it. `src/repo/isolation.test.ts` is the cross-user test; extend it when adding repos.
- `src/auth/*`: argon2id login, opaque session token (cookie holds the token, DB stores its sha256), sliding 30-day expiry, `originCheck` CSRF guard (JSON POSTs bypass `hono/csrf`, hence the custom one), login rate limit (8 failures per IP, 30 per username, per 15 min, in memory; `loginLimits()` in `rateLimit.ts`, built once in `createApp` and shared by login, the current-password check and Manage users, whose reset and re-enable lift a user's lockout). The IP is the socket peer, or the rightmost `X-Forwarded-For` entry when the peer matches `TRUST_PROXY` (`clientIp.ts`: IPs, CIDRs, hostnames re-resolved each minute, or `true`; behind a tunnel, set it to the tunnel container's name, since traffic to the published port arrives from the Docker gateway and must not be trusted). `CF-Connecting-IP` is not read. Known devices (`device.ts`): a signed `cairn_device` cookie (user id, HMAC secret in `app_setting` `device_cookie_secret`, path `/api/auth`, 400 days, kept across logout) is set on login and on `/me` when missing; a browser carrying it for the user skips the per-username limit (its failures don't count and its success doesn't reset the counter), so hammering a username can't lock the owner out of their own devices. Tests that fake client IPs pass `trustProxy: () => true` and `x-forwarded-for`. `requireAuth` reads the session joined to its user and sets `userId` and `role` on the context (fresh every request, so a demotion or disable bites at once; a disabled user's session is refused and deleted); `requireAdmin` answers 403 `forbidden`. The cookie is `Secure` only when the request arrived over https (`X-Forwarded-Proto`), so plain-http access on a LAN or VPN still works.
- `src/app.ts`: `/api/health` and `POST /api/auth/login` are public; everything else under `/api` requires a session (unknown routes 401 when logged out). Server-wide routes are admin only, gated in `app.ts` before their routers: `/places/key` (all methods), `PUT /attachments/limit`, `/backup/*`, and `/admin/*`. `GET /attachments/limit` stays open (every uploader needs it). A new server-wide route needs the same gate and a non-admin 403 case in `admin.test.ts`. Every request body is capped at `MAX_JSON_BODY_BYTES` (2 MB, 413 `too_large`) before anything reads it, the public login included; the routes in `UPLOAD_ROUTES` (photos, attachments, import, avatar) are left to their own limits, and a new upload route must be added there (`bodyLimit.test.ts`).
- Entry has two sets of dates: `created_at`/`modified_at` are the entry's own (user-editable, Day One's creationDate/modifiedDate); `updated_at`/`deleted_at`/`rev` are row-level sync columns.
- Migrations: `runMigrations` takes a `VACUUM INTO` snapshot (`/data/backups/pre-migrate-*.db`, last 5 kept) before applying anything to an already-migrated DB, runs all pending ones in one transaction, and throws on failure so the server exits.

## API

Routes live in `src/routes/*` and only use `createRepos` (via `reposFor`). Request/response shapes are Zod in `packages/shared/src/api.ts`; responses use explicit field lists (no `source_raw`, file paths, hashes or user ids).

- `GET/POST /api/journals`, `PATCH/DELETE /api/journals/:id` (journals carry an optional `description`, trimmed, max 1000, empty = null; it rides the sync feed and the `cairn` export extras; Day One's own export has none; list includes archived, told apart by `archivedAt`; delete also tombstones the journal's entries, all with the journal's own `deletedAt`, which the trash's restore relies on). `PUT /api/journals/order {ids}` sets sort order = position (ids not listed follow; unknown, deleted, duplicate and other users' ids are skipped, since a client's list can be stale; only journals that moved get a new rev); a new journal gets `max(sort_order)+1`.
- `GET /api/entries?journalId&cursor&limit&includeArchived`: timeline cards, pinned entries first (as in Day One), then newest first; keyset cursor on `(pinned, created_at, id)` (a pinned cursor is `P<created_at>_<id>`, `decodeCursor` in `packages/shared`). Search, the map, the calendar and the media feed ignore pins. Archived journals are hidden unless `includeArchived` or `journalId` names one.
- `GET/PATCH/DELETE /api/entries/:id`, `POST /api/entries`. Create is idempotent on a client-supplied `id`. PATCH takes `baseRev`; a mismatch is `409 {error:'conflict', current}`. Entries in an archived journal are read-only (`409 journal_archived`), including moving one in. Another user's id is always a 404 (`id_taken` 409 only when creating).
- `GET /api/photos/:id/(original|display|thumb)`: ownership-checked, ETag + immutable private caching; display/thumb fall back to the original when no derivative exists.
- `PUT /api/attachments?name=`, `GET/DELETE /api/attachments/:id`, `GET/PUT /api/attachments/limit`: see `src/attachments/CLAUDE.md`. Entry details carry `attachments` beside `photos`.
- `GET/PUT /api/import`, `POST /api/import/:id/start`, `DELETE /api/import/:id`: importing a Day One or Cairn export zip into the caller's own account from Settings; see `src/import/CLAUDE.md`. Any user (not admin-gated); the upload is capped by the attachment limit.
- `GET/PATCH /api/auth/me`: `defaultJournalId` is the effective default (see Web app); PATCH `{defaultJournalId: id|null}` chooses it (404 unknown, 409 archived). Journals carry `entryCount`. PATCH also takes `displayName` (trimmed, 1-100), `defaultTimezone` (an IANA zone; `TimezoneSchema` in `packages/shared` checks it with `Intl.DateTimeFormat`, 400 otherwise; it only changes how Insights and the Calendar bucket days, entries keep their own zone), `tempUnit`, `autoLocation`, `showArchivedInMenu` (the nav's Archived fold; on by default), `showStreak` and `showBestStreak` (hide the streak stats in Insights and the Details view; on by default). The entry font and size are per device, not on `me`. Me also carries `avatarUpdatedAt` and `role` (`user`/`admin`).
- `POST /api/auth/credentials {currentPassword, username?, newPassword?}` (account settings): the only place a username or password changes, apart from the CLI. A wrong current password is 403 `wrong_password` and counts against the same `FailureLimiter`s as login (so it is 429 `rate_limited` after too many); `username_taken` is 409 (usernames are lowercased); a new password (`NewPasswordSchema`, 8-1024 characters; login still takes any non-empty one so older passwords work) ends every other session of the user (`deleteSessionsOf` in `repo/sessions.ts`) and keeps the calling one.
- `GET/PUT/DELETE /api/avatar` (`routes/avatar.ts`, `photos/avatar.ts`): the caller's own profile picture, no id in the path so nobody can name another user's. PUT takes the raw image (JPEG/PNG/WebP sniffed with sharp, 10 MB, 415 otherwise), auto-rotates, centre-crops to a square, resizes to 256px WebP and keeps only that (not the original: the keep-the-original rule is for entry photos) at `photos/<user_id>/avatar.webp`, so backups cover it; `user.avatar_updated_at` versions it and is strictly increasing. The web asks for `/api/avatar?v=<avatarUpdatedAt>` (the server ignores `v`; the response is `immutable`). Not exported (Day One has no field for it). It is no `photo` row, so `photos/gc.ts` never touches it and the export only copies files its entries reference.
- Manage users (`routes/admin.ts`, admins only; schemas `AdminUser*`, `CreateUserSchema`, `UpdateUserSchema`, `ResetUserPasswordSchema` in `packages/shared/src/auth.ts`): `GET /api/admin/users` (id, username, display name, role, disabled, created; nothing about journals; no paging, a family at most), `POST /api/admin/users {username, displayName, password, role?}` (201; the password is a temporary one, no forced change; the new user starts in the admin's default timezone; `username_taken` 409), `PATCH /api/admin/users/:id {role?, disabled?}` (disabling ends all their sessions), `POST /api/admin/users/:id/password {newPassword}` (ends all their sessions). On your own id both are 409 `self` (use Account, which asks for the current password); a change that would leave no enabled admin is 409 `last_admin`. Login for a disabled user with the right password is 403 `account_disabled`. Roles live on `user.role`, disabled on `user.disabled_at`; `seedInitialUser` creates an admin. No hard delete. Admins get no route to anyone else's content: `admin.test.ts` checks the 403s and that an admin gets 404 on another user's journals, entries, photos and attachments.
- Storage (`storage/usage.ts`, rows from `repo/storage.ts`, file helpers `storage/files.ts`; schemas in `packages/shared/src/storage.ts`): `GET /api/storage` is the caller's usage, `GET /api/admin/storage` (in `routes/admin.ts`, so admin-only) is every user's plus the server's (`cairn.db` with `-wal`/`-shm`, and `backups/`; not free disk space, which under Docker Desktop/WSL2 is the virtual disk's maximum, not the host drive). Sizes come from the files on disk (`fileSizes`, stat'd 200 at a time, also used by `/api/sync/estimate`), never from the `bytes` column (that is only the uploaded original's size). A file shared by several rows counts once in a total and in every journal that shows it. Media rows are "shown" when they and their entry are live; files a live media row of a trashed entry uses (and no shown row) are `trash`; files only other rows point at (deleted, never attached, in a purged entry) are `pending`. The admin report gives each user's totals only, nothing per journal (`admin.test.ts` checks nothing leaks). Computed on every request; nothing stored. `GET /api/admin/cleanup` previews the cleanup (`maintenance.ts`: the trash's expiry, then `photos/gc.ts`; a dry run) and `POST` runs it; counts only, the paths of missing files go to the server log. `GET/PUT /api/admin/photos` is the photo quality setting (`app_setting` `photo_quality`, `photos/quality.ts`; pinned at startup) plus the compress-existing job, `POST /api/admin/photos/compress` starts it (409 unless the setting is `compressed` and a backup succeeded within 24h; `photos/compressExisting.ts`, state in memory).
- Server alerts (`health/`, schemas in `packages/shared/src/health.ts`; admin routes in `routes/admin.ts`): `notify.ts` keeps the ntfy settings in `app_setting` (`ntfy_enabled`, `ntfy_url` default `https://ntfy.sh`, `ntfy_topic`, `ntfy_token`; the token is write-only: `GET /api/admin/notifications` returns `hasToken`, and a PUT without `token` keeps it, an empty one removes it) and `sendAlert` (POST to `<url>/<topic>`, 10s timeout, no redirects, never throws, the error text never holds the token). `check.ts` `checkHealth` measures what the alerts watch: the backup state from `backup/status.ts` (`failing` or `stale`; `none` = not set up = not a problem) and a real write to `app_setting` (`health_probe`) for a database that can't be written (this also catches a full disk once it bites). Free disk space is deliberately not watched or shown: under Docker Desktop/WSL2 the container sees the virtual disk's maximum, not the host drive, so a threshold would never fire (the same reason Storage doesn't show it). `monitor.ts` `healthMonitor` turns that into messages: one when a problem starts, a reminder after 24h, one when it clears; a failed send is retried next tick; off clears its memory (state is in-process, so a restart announces a standing problem once more). `index.ts` ticks it a minute after start and every 15 minutes. There are no per-alert switches: on means all of them. `GET /api/admin/health` (live), `PUT /api/admin/notifications`, `POST /api/admin/notifications/test`; all admin only. Messages carry alert text only, never anything from entries. A container restart is deliberately not alerted (that is an outside uptime monitor's job).
- Trash (`repo/trash.ts`, `routes/trash.ts`, schemas in `packages/shared/src/trash.ts`): a deleted entry or journal is in the trash while `deleted_at` is set and `purged_at` null. `GET /api/trash/entries?cursor&limit` (entries whose journal is live, newest deleted first, keyset on `(deleted_at, id)`, the timeline card plus `deletedAt`/`purgeAt`), `GET /api/trash/journals` (with `entryCount`: entries whose `deleted_at` equals the journal's), `GET /api/trash/count`, `GET /api/trash/entries/:id` (one trashed entry in full as an `EntryDetail` plus `deletedAt`/`purgeAt`, to read before restoring; 404 when live, purged, or its journal is in the trash too; `trashRepo.entryDetail` reuses `entryRepo`'s `detailOf`, whose media rows are still live); `POST /api/trash/entries/:id/restore` (409 `journal_deleted` or `journal_archived`), `POST /api/trash/journals/:id/restore` (the journal and the entries deleted with it; entries deleted on their own before it stay in the trash), `DELETE /api/trash/entries/:id`, `DELETE /api/trash/journals/:id` (with every trashed entry in it), `DELETE /api/trash` (empty). Restore bumps the rev of each entry **and its live photos and attachments** (clients drop an entry's media when it is deleted) and re-indexes search. Purging (`purgeEntries`) sets `purged_at`, clears `body_md`, `source_raw` and the mood fields, deletes the place, weather and tag rows (and tags left unused), keeps `source_id` (a re-import still skips it, unless the importer's `--force` (`reimportPurged`), which clears the tombstone's `source_id` and imports a fresh copy) and bumps no rev: the row stays as a tombstone for sync. Retention is the admin setting `GET/PUT /api/admin/trash {retentionDays}` (`app_setting` `trash_retention_days`, one of `TRASH_RETENTION_DAYS`, default 60, read on every use; also on `/me` as `trashRetentionDays`). `purgeExpiredTrash` (maintenance, all users) runs before the media cleanup in `maintenance.ts` `runMaintenance`, which the daily sweep and `/api/admin/cleanup` both call; the cleanup report carries `expiredEntries`/`expiredJournals`. Tag `merge` and a `rename` over a tag only trashed entries carry move those entries' join rows, so a restore keeps its tags. Storage counts trashed entries' text and the files only they use as `trash` (`trashBytes` per user for admins), apart from `pending`.
- Writing prompts (`repo/prompts.ts`, `routes/prompts.ts`, schemas and limits in `packages/shared/src/prompts.ts`; design in `docs/design/prompts-proposal.md`): one `prompt` table, two scopes kept apart as separate function sets. `userPromptRepo` (on `createRepos` as `prompts`) always filters `user_id`; `suggestedPromptRepo` (`user_id IS NULL`, the admin's server-wide list) and `promptCategoryRepo` are server-wide and imported directly by the routes (no user id, like `appSettingsRepo`). Settings-like data: no rev, tombstones or sync; rows are deleted outright. `GET /api/prompts/categories|suggested` are open to any session; every write to them (`POST/PUT/PATCH/DELETE` under `/prompts/categories` and `/prompts/suggested`, including `PUT /categories/order` and `POST /suggested/import`) is gated by `requireAdmin` in `app.ts`, so a new route under those paths is admin-only automatically. `/prompts/mine` (GET, POST, PATCH/DELETE `:id`) is the caller's own; `POST /mine/from-suggested {ids}|{categoryId}` copies suggested prompts, skipping any the user already has a copy of (`source_prompt_id`, no FK, so deleting a suggestion leaves copies) and replies `{saved}`. A prompt has at most one category; deleting a category sets `category_id` null on prompts and never reads their text. Names match ignoring case. Caps (409 `limit_reached`): 200 characters, 2000 prompts per user, 2000 suggested, 30 categories. `POST /mine/bulk-delete {ids}` and `POST /suggested/bulk-delete {ids}` (admin, by the same gate) delete up to 2000 at once and reply `{deleted}`; ids that aren't in that scope (another user's, a suggested id on `/mine`, unknown) are skipped, so the count can be lower than the list. The JSON import (`{categories:[{name, icon?, prompts[]}]}`, 1 MB, 500 prompts; `{file, dryRun}`) merges only and answers with a summary; an unknown icon (not in `PROMPT_ICONS`) is counted and the default is used. The cross-user checks are in `prompts.test.ts` (not `isolation.test.ts`), including that an admin gets 404 on another user's prompts.
- Entry templates (`repo/templates.ts`, `routes/templates.ts`, schemas and limits in `packages/shared/src/templates.ts`): a user's saved text, a name plus a markdown body, inserted into an entry by the editor (placeholders such as `{{date}}` are the client's business, the server stores the text as typed). One `template` table, per user only (no server-wide list, no admin routes). `templateRepo` is on `createRepos` as `templates` and always filters `user_id`. Settings-like data like prompts: no rev, tombstones or sync feed, rows deleted outright. `GET /api/templates` (by name ignoring case, then oldest), `POST` (201), `PATCH /:id` (`name` and/or `bodyMd`; an empty change is 400), `DELETE /:id` (204). Another user's id, an admin's included, is a 404. The name is trimmed (1-80); the body is kept exactly as sent (up to 20,000, never blank). Cap 100 per user, 409 `limit_reached`. Not exported (Day One has no templates; saving one as an entry is the workaround). The cross-user checks are in `templates.test.ts`.
- Make-admin CLI (`auth/makeAdmin.ts` core, `auth/make-admin-cli.ts`; bundled to `dist/make-admin.js`, shipped as `make-admin.js`): the escape hatch for a server with no usable admin; sets the role to admin and re-enables the user.
- Password reset CLI (`auth/resetPassword.ts` is the testable core, `auth/reset-password-cli.ts` the TTY / `--password-stdin` wrapper; bundled to `dist/reset-password.js`, shipped as `reset-password.js` next to `import-journal.js`): sets the hash and deletes all of the user's sessions (it doesn't re-enable a disabled user; `make-admin.js` or an admin does).
- `GET /api/sync/changes?since&limit&journalIds` (`repo/sync.ts`, `routes/sync.ts`, schemas `Sync*` in `packages/shared/src/api.ts`): everything after a revision, oldest first, across journals, entries (without media), photos and attachments (their own records, since one can change without its entry's rev moving). One per-user rev counter covers all four, so one cursor does. Each table is queried for `limit` rows and the merge is cut at `limit`, so nothing is skipped. Deletes are `deleted*Ids`. `journalIds` limits entries and their media; after the first page a change outside it arrives as a deleted id (an entry moved out of a synced journal). `reset: true` means `since` is ahead of the server (restored backup): the client must wipe and restart from 0. Entries sit in the feed at `max(rev, weather_rev)`: `setFetchedWeather` stamps `weather_rev` from the same counter and still leaves `rev` alone. Anything new that changes what a client shows must bump a rev the feed reads (or add its own column the way weather did).
- Tags (`repo/tags.ts`): create and PATCH take `tags: string[]` (omit = leave alone, `[]` = clear), resolved case-insensitively with the first spelling kept (`resolveTags`, shared with the importer; `tagKey` in `packages/shared`); the unique index is on `lower(name)`. `writeEntryTags` replaces the join rows and deletes a tag no entry carries any more, so tag rows are never orphaned; the entry's rev bumps (every PATCH does) and `indexEntry` runs. `GET /api/tags` lists `{name, count}` of live entries, most used first; `GET /api/entries?tag=` filters the timeline (case-insensitive). Tag lists are ordered by `lower(name)`. Managing (`rename`, `merge`, `remove` in `repo/tags.ts`; routes `PATCH /api/tags {name,newName}`, `POST /api/tags/merge {from,into}`, `DELETE /api/tags?name=`, each replying `{entries}`): tags are addressed by name, never an id. Every live entry that carried the tag gets a new rev (so the sync feed re-sends it with the new tag names) and a rewritten search row, but its own `modified_at` is untouched. A rename onto a different existing tag is `409 tag_exists` (the UI then offers a merge); a case-only change is fine; a leftover tag only deleted entries carry is dropped to make way. Merge keeps `into`'s spelling; delete removes the tag from its entries and deletes the tag row (hard, like the orphan cleanup; tag rows aren't synced). Unknown names are 404.
- Media feed (`repo/gallery.ts`, `routes/media.ts`): `GET /api/media?journalId&kinds=photo,video,audio,pdf&cursor&limit` lists photos and attachments of live entries, newest entry first, for the web's Media view. Two tables, so each is read `limit + 1` past the cursor and merged; the cursor is `encodeCursor(entry createdAt, media id)` with the tiebreak on the media id (not the entry id, or two files of one entry would repeat forever). Archived journals are left out unless one is named, like the timeline.
- Insights (`repo/insights.ts`, `routes/insights.ts`, pure maths and schemas in `packages/shared/src/insights.ts`): computed on demand, nothing stored, because SQLite can't group by day in an IANA zone and a stored local date would drift when an entry's time is edited. SQL narrows to a UTC window widened by 14h (`MAX_UTC_OFFSET_MS`), then `localDayHour` buckets by each entry's own zone. `GET /api/insights/stats?today=YYYY-MM-DD&range=week|month|all` (total, days, words and time of day over the range; streaks are all-time, the current one ends today or yesterday; `topTag` is the most used tag in the range, ties by name), `/month?month=YYYY-MM` (per day: entries, `mood` = most frequent mood (ties to the latest), `moodKinds` = how many different moods, `valence` = mean valence of the rated entries, `entryId` when the day has exactly one entry, and `journalIds`, the journals its entries are in), `/details?today=` (entries, distinct local days, photos plus files, first and last day, words (`countWords`: photo and file references don't count) and the current and best streak, for the Details view; takes `journalId`; archived journals count only when named), `/day?date=` (that day's cards, newest first), `/first-month` (`month` of the oldest entry, or null, taken 14h early so it can be an empty month but never too late, and `lastMonth` of the newest, taken 14h late; the calendar runs to the later of that and two months past today); `/months` (the months, oldest first, with an entry on one of their local days: the entry list's month picker; archived journals only when named), `/month` and `/day` and `/first-month` take an optional `journalId` that narrows them to one journal (the Entries calendar), `/on-this-day?date=` (earlier years' cards, newest year first; Feb 29 only matches leap years). Archived journals are left out of all of Insights (stats, calendar, mood averages, the day list and On this day), like the Entries list. The client names "today" so the server needs no clock rules. Revisit with a stored `local_date` only if journals reach ~50k entries.
- Drafts are deliberately not on the server (SPEC section 3, Phase 7).
