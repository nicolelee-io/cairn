## Weather

- Providers implement `WeatherProvider` (`weather/provider.ts`: `lookup(lat, lng, at, now)` returns a `NewWeather`, null when there is nothing for that time, or throws `WeatherError`). The admin picks one (Settings > Server > Weather source, `GET/PUT /api/admin/weather`, `app_setting` `weather_provider`, `weather/settings.ts`; default **Open-Meteo**; choosing Google without a saved key is `409 google_key_needed`). `googleKeys(...).weather()` (`places/index.ts`) returns the chosen provider, or undefined for Google with no key.
- `weather/openMeteo.ts` (`openMeteoWeather`, the default): no key, free for non-commercial use under CC BY 4.0 (the About card credits it). Hourly values at the nearest UTC hour from the forecast API (`past_days=5`) for the last 5 days and from the archive API (one day) for anything older, so backdated entries get weather; only the future (more than 30 minutes ahead) returns null. WMO `weather_code` maps through `mapWmoWeather` in `packages/shared/src/weather.ts`; pressure is `pressure_msl` (sea level, like Google's); no description or visibility. Failures throw `WeatherError` with the status and Open-Meteo's `reason`.
- `weather/google.ts` (`googleWeather`): Google Weather API, `currentConditions:lookup` for an entry within 10 minutes of now, `history/hours:lookup` (24 hourly records, the one whose interval contains the entry time) up to 23h back, and for a time under 2 hours old that the history has no hour for yet, the live reading; older or in the future returns null. Condition types map through `mapGoogleWeather`; the raw type stays in `source_code`. It uses the same key as places, passed as a query parameter.
- Stored `source` is `dayone`, `google`, `open-meteo` or `manual` (`WEATHER_SOURCES`). Weather from a provider (`isAutoWeather`) is what a new place or time replaces and a refetch overwrites, whichever provider made it; Day One's and hand-entered weather are never touched. Changing the provider leaves existing weather as it is.
- `weather/service.ts` `refreshWeather`: the background job. `routes/entries.ts` fires it after any create/PATCH that leaves an entry with a place and no weather (new place, entries whose place predates weather, weather dropped for "automatic"), and when the place or time changed on an entry whose weather came from a provider (`isAutoWeather`). Out-of-range entries make no request. Failures are logged and ignored (`routes/entries.ts` `autoWeather`). It never replaces Day One or manual weather and **does not bump the entry's rev** (`setFetchedWeather`), so a fetch landing after a save can't make the editor's baseRev stale; it stamps `weather_rev` instead, which the sync feed reads.
- The editor previews weather as soon as there is a place: `weatherAfterMove` (`lib/weather.ts`) turns weather nobody chose by hand into `{auto: true}` whenever the place or time changes (hand-entered and Day One weather stay; Google's follows), and the chip shows what `GET /api/weather/preview?lat&lng&at` returns (nothing is stored). It answers 404 `no_weather` when the provider has nothing for that time (normal), 424 `weather_unavailable` (Google chosen, no key) or 424 `weather_failed` (the provider failed; the reason is in the server log); `EntryMetaBar` turns those into "No weather for this time" and "Weather unavailable" on the chip. The stored weather is still the server's own (the client only ever sends hand-entered values, which are stored as `manual`; sending the preview's would freeze it and skip `source_code`), but Save reuses the preview's answer: `weather/cache.ts` `withWeatherCache` wraps whichever provider `googleKeys().weather()` returns with a 10-minute, 100-entry in-memory cache (keyed by provider, exact coordinates and the entry's 10-minute bucket; only answers are kept, never a failure or a null; the store lives in the `googleKeys` closure, since a provider object is made per call). On a create or PATCH, `routes/entries.ts` `autoWeather` first tries `refreshWeatherFromCache` (`weather/service.ts`: no request, `miss` when nothing is cached), and on a hit stores the weather before building the response, so the saved entry already carries it and the reader opens with the chip; on a miss (preview not finished, offline queue replay, a time edited since) it falls back to the background `refreshWeather`. A save that removes weather (`weather: null`, on create or PATCH) is respected: no refetch.
- Weather is edited like the place, in the editor, and saved with Save: create takes `weather` (manual), PATCH takes `weather` = manual values, null (remove) or `{auto: true}` (drop it and refetch after the save). The draft carries it (`lib/weather.ts` `sameWeather`). The reader shows it read-only; the entry query re-polls a few times after a save so background weather appears.
- Auto location: `user.auto_location` (`PATCH /auth/me {autoLocation}`, a Settings switch). When on, `EntryEditor` on a new entry that isn't a restored draft asks the browser for its position (`lib/geolocate.ts`), reverse-geocodes it (bare coordinates if that fails) and puts it in both the fields and the baseline, so an untouched entry isn't kept as a draft; weather then follows from the normal save-time fetch. Refusal or failure leaves the place empty. Geolocation needs https or localhost.
- °F/°C lives on the user (`user.temp_unit`, `PATCH /auth/me {tempUnit}`, Settings), so every device agrees; `lib/tempUnit.ts` holds the current value for `formatTemp()` and is set whenever `me` loads or changes. Storage stays °C. Not built: the optional "home" location for entries with no place.
