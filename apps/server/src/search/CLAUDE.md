## Search

- `entry_fts` is an FTS5 table (hand-written migrations: Drizzle can't model virtual tables) with columns title, body, place, tags and unindexed `entry_id`/`user_id`; the title is the card's title line and the body is the rest (`splitTitle`, in `packages/shared/src/plainText.ts` and re-exported by `src/entryText.ts`, which also re-exports `summarize`, so cards and index agree on what the title is; a test pins that); tokenizer `porter unicode61 remove_diacritics 2`, so "walking" finds "walked" and "cafe" finds "café". Each row's rowid comes from `entry_fts_key` (`fts_rowid INTEGER PRIMARY KEY`, which VACUUM never renumbers, and a unique `entry_id`; one per entry, kept for good), so removing an entry's row is an index lookup plus a delete by rowid, not a scan of the unindexed `entry_id` column; `rebuildIndex` clears both tables.
- `src/search/index.ts` keeps it current from the repo layer, inside the writing transaction (`indexEntry` / `removeFromIndex` / `removeJournalFromIndex`): entry create, text edit and delete, the importer, and journal delete. SQL triggers can't do it because the markdown is stripped in code (`markdownToPlain` in `packages/shared/src/plainText.ts`, shared with the device's offline search: no image or link targets, so `photo:<id>` and URLs never match; Day One escapes undone). **Anything that edits tags or location must call `indexEntry` too** (`update` in `repo/entries.ts` does, for both). Only the text is indexed on edit; starred, journal and dates are read from `entry` at query time, as are tombstones and archived-ness (so a stale index row can't leak a deleted entry).
- Startup runs `ensureSearchIndex`: if `search_state.index_version` differs from `INDEX_VERSION` (or is missing) the whole index is rebuilt. Bump the constant when what is indexed changes. Journal names are deliberately not searchable.
- `search/match.ts` turns typed text into a MATCH expression: letters and digits only, words ANDed (explicitly: FTS5 rejects an implicit AND next to a group), "quotes" for a phrase, last word as a stemmed prefix. FTS syntax in user input can never reach SQLite.
- `GET /api/search?q&sort=newest|relevance&journalId&starred&attachments&tag&mood&from&to&includeArchived&cursor&limit` (`repo/search.ts`) returns timeline cards plus `snippet` (body text, else tags or place, around the match) and `snippetField` (`body|tags|place`, which of those it is). `tag` keeps entries carrying that tag (resolved ignoring case by `findTagId`; an unknown tag is no results) and, like Starred and Attachments, lets `q` be empty (as do `mood` (a mood key, matched on `entry.mood_key`) and `from`/`to`, days `YYYY-MM-DD` inclusive, read in each entry's own timezone: SQL narrows by the UTC window widened 14h (`dayWindowUtc`), then `dayInRange` in `packages/shared/src/insights.ts` checks the real local day in code, and since that breaks LIMIT/OFFSET a ranged search reads up to 5000 candidates and pages them in code; the offline search in `localRead.ts` uses the same `dayInRange`) and `titleMarked`, with `SNIPPET_OPEN`/`SNIPPET_CLOSE` around matched words; a title match weighs most in Best match. `GET /api/search/matches?q&entryId` returns the words of one entry that the query matched (as written, so "walking" reports "walked"). The FTS query is a MATERIALIZED CTE because snippet()/bm25() fail once the outer query joins or re-sorts. Cursor is an offset (results are re-ranked each request). Archived journals are excluded unless `includeArchived` or `journalId` names one. Cross-user case is in `isolation.test.ts`.
- Offline the device answers `/search` and `/search/matches` itself from the journals it keeps (`apps/web/src/lib/localSearch.ts`, see `apps/web/src/lib/CLAUDE.md`): the same word rules minus stemming and ranking. A change to what the index holds or how words match should be mirrored there.
- Web: `pages/SearchPage.tsx` keeps everything in the URL (`?q=&sort=&starred=1&archived=1&j=&tag=&mood=&from=&to=`; the everyday filters (Starred, Journal, Tag, Sort) are always shown and the rarer ones (Attachments, Include archived, Mood, From, To) sit behind a "More filters" toggle that shows how many are on and starts open when one is; Mood is a `Select`, From and To are chips (`DayField`) that open the editor's `Calendar` in a dialog with a box below it to type a day (a muted hint appears only after the box is left with something unreadable) (`lib/parseDay.ts`: `MM/DD/YYYY` or `YYYY-MM-DD`, Enter or Set applies, the calendar follows what is typed), and setting one end past the other drops the other), debounces typing, reuses `EntryCard` (`snippet`, `titleMarked`, `showDate`) and renders highlights as React text (`components/Marked.tsx`, `lib/search.ts`), never HTML. Results link to `/entry/:id?q=...`; the reader asks `/search/matches` and `Markdown` marks those words through a small rehype plugin (`lib/highlightWords.ts`, text nodes only). `lib/useLoadMore.ts` is the shared infinite-scroll sentinel, and `lib/useWindowScroll.ts` (in `AppShell`) puts the window back where it was on Back/Forward.
