## Importer

- `src/import/`: `cli.ts` (the importer CLI, below) and `dayone/` (the Day One format reader): `source.ts` (zip via yauzl, or extracted folder), `map.ts` (zod shapes, pure mapping, placeholder rewrite), `run.ts` (orchestration). `cli.ts` (path, folder or `-` for a zip on stdin, spooled to `imports/cli-<pid>.zip` and removed on exit; `scripts/import.sh` wraps it with backups). DB writes go through `repo/imports.ts`. An entry already there (by Day One uuid, or the Cairn id of our own export) is skipped, even once purged from the trash; `--force` (`reimportPurged`) skips only live and trashed ones, clearing a purged tombstone's `source_id` (the `(user_id, source_id)` unique index) and importing a fresh copy under a new id.
- Photos: the original is copied to `photos/<user_id>/originals/<sha256>.<ext>` (relative to the data dir; or compressed to `compressed/<sha256>.jpg` under the server's photo quality setting, `storeOriginal`), with `display/` (~2048px) and `thumb/` (~400px) WebP derivatives beside it, made by `src/photos/pipeline.ts` (sharp, auto-rotated, no metadata). EXIF GPS and date go to the DB columns, never into derivatives. If a file can't be decoded the original is kept, derivative columns stay null, and the report warns. Inline images are rewritten to `![](photo:<id>)`; the renderer must resolve that scheme.
- Attachments (`videos`, `audios`, `pdfAttachments`; the table is `ATTACHMENT_LISTS` in `map.ts`, shared with the export): the original goes to `attachments/<user_id>/<sha256>.<ext>` streamed from the zip or folder (`source.openFile`) through `storeAttachmentStream` (to a temp file while hashing, like an upload, so a long video never sits in memory; type from the bytes, else the declared one with a warning), placeholders become `![name](attachment:<id>)`. Name: `cairn.filename`, else `pdfName.pdf`, else `video.mp4`/`audio.m4a`. Positions follow Day One's order, like photos.
- **Import from Settings** (`import/jobs.ts`, `routes/import.ts`, schemas in `packages/shared/src/import.ts`; the API is named for importing, not for Day One: Day One's JSON zip and Cairn's own export, which is that format plus `cairn` extras, are read alike). `PUT /api/import?name=` streams the raw zip to `imports/<id>.zip` in the data dir (capped by the attachment limit, `attachments/limit.ts`; 413 `too_large`), opens it with yauzl and runs `dayone/preview.ts` `previewDayOne` (no writes: journals named as the importer names them, entry counts, how many `hasSource` already finds, whether the journal exists or is archived, photo and file counts), answering 201 with the preview; not a zip, no root `.json`, or a journal file without an `entries` list is 415 `unsupported_format` and the file is deleted. Journal JSON is parsed whole, so the preview refuses journal files that unpack past `MAX_JSON_BYTES` (64 MB, from the zip's `uncompressedSize`, which yauzl enforces) as `too_large`. Media is capped too, so a small zip can't unpack into gigabytes: the upload is `too_large` when everything but the journal files would unpack past `MAX_MEDIA_RATIO` (2) times the upload limit (`ZipSource.unpackedBytes`; real media hardly compresses), and the run passes `importDayOne` `maxPhotoBytes` (50 MB, as for an upload) and `maxAttachmentBytes` (the attachment limit), checked against `fileSize` before a file is read: an entry with a bigger one fails and is reported (never imported without it), and the CLI, which sets neither, is the way to bring it in. One upload waits per user (a new one replaces it), for `STAGED_FOR_MS` (1h, expired lazily on any call). `POST /api/import/:id/start {archived}` (202) runs `importDayOne` in the background with the user's default timezone; `GET /api/import` is `{staged, job, busy}` (progress summed over journals via `onProgress`'s journal name; at the end a report with warnings and failures capped at 50 lines); `DELETE /api/import/:id` drops the upload. Another user's id is a 404, admins included. One run at a time on the server (`import_busy` 409; also refused for a user's own new upload while theirs runs). State is in memory: `index.ts` `clearImportUploads` empties `imports/` at startup, and a run cut off by a restart is finished by uploading the same zip again. Errors in a run go to the server log; the app gets a fixed line (disk full, or "something went wrong"). The backup doesn't cover `imports/` (only the DB, `photos/` and `attachments/`). Tests: `import/jobs.test.ts`.
- Weather uses the canonical enum in `packages/shared/src/weather.ts`; unmapped codes become `unknown` with `source_code` kept.
