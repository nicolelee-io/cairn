## Photos

- `POST /api/photos` (multipart field `file`, one per request, 50MB cap, JPEG/PNG/WebP/GIF/AVIF/TIFF sniffed from the bytes (sharp calls AVIF `heif` with `av1` compression, `formatOf` in `upload.ts`; HEIC is `heif` with `hevc`, which the prebuilt libvips can't decode); HEIC and others are a 415 with a message; a GIF's derivatives are its first frame, the original keeps the animation) runs `photos/upload.ts` (original + display + thumb, deduped files by sha256) and returns the photo.
- Photo quality (`photos/quality.ts`; SPEC section 7): `storeOriginal`, used by uploads and the importer, writes the original as uploaded (`originals/<sha>.<ext>`) or, under `compressed`, as `compressed/<sha of the upload>.jpg` (`compressImage` in `pipeline.ts`: JPEG and opaque PNG only, at most 4096px, q85, `keepMetadata`, kept only at 90% of the size or less). The row's `sha256` stays the upload's (dedupe), `mime`/`bytes` describe the stored file, width/height the upload (same aspect ratio). The original route's ETag is `"<sha>-compressed"` for these. `compressExisting.ts` converts stored originals one file at a time: compress, then synchronously write, repoint every row on that path (no `rev` bump: clients never hold originals), delete the old file. The row has `entry_id` NULL until the entry that references it is saved. `DELETE /api/photos/:id` tombstones it (files stay) and strips its reference from the entry body.
- The entry text is the source of truth. `syncEntryMedia` (`repo/media.ts`, shared with attachments), called inside entry create/update when the body changes, attaches unattached photos the body references, tombstones photos the edit removed from the text, and sets `position` from order of appearance (so reordering is moving the line; there is no reorder endpoint). Only photos newly removed from the text are tombstoned, so imported photos the text never mentioned are safe. Reference helpers (`photoRefs`, `stripPhotoRef`, `swapPhotoRefs`, and the `attachment*` twins) live in `packages/shared/src/mediaRefs.ts` and are used by both sides.
- Editor: toolbar button, paste and drop on the text area -> `useUploads` (sequential, XHR for progress; attachments go the same way) -> `insertBlock` at the caret; the editor renders referenced photos inline (`cm/livePreview.ts`); `PhotoStrip` shows them only in source mode, plus loose photos and upload progress. Save is disabled while an upload is running. Drafts need no photo state: the reference is in the text.
- Photos the text never mentions (Day One allows that) show in the reader after the text and in the editor strip as "Add to text" / remove; removing sends `removeMediaIds` with the PATCH (photos or attachments; only ones not referenced by the new body are tombstoned; the old name `removePhotoIds` is still accepted for queued outbox saves).
- Cleanup (`photos/gc.ts` `collectMediaGarbage`, run by `maintenance.ts` after the trash's expiry at startup, daily, and from the admin Server storage page, for attachments too; synchronous, so runs never interleave): uploads never attached to an entry after 24h are tombstoned, and so are the media of purged entries (deleted for good from the trash, `repo/trash.ts`), with the entry's `purgedAt`; media of entries still in the trash stay live, however old, so a restore gets them back whole; files of rows tombstoned over 30 days ago, or of purged entries at once (the trash was their undo window), are deleted unless a live or recently deleted row uses the same file; files in a known user's folders that no row of any state names are deleted after 24h (`.tmp` after 1h; never `avatar.webp`), so `storeOnce` and the attachment upload touch a reused file's mtime; live rows whose file is gone are counted and logged, never changed. `dryRun` reports the same numbers and changes nothing. Tombstone rows stay for sync. Uploads are capped at 100 megapixels (`MAX_PIXELS`).
- Reader: `Lightbox` (native `<dialog>`) opens from any photo in `Markdown`/`PhotoImage` via `onOpenPhoto`; the editor's inline photos open it too.
