## Export

- Settings > Export downloads `GET /api/export`: Day One JSON plus `cairn` extras that Day One ignores. Every extra is something the importer reads back; don't add one that isn't. **Nothing except journals may end in `.json` anywhere in the archive** (Day One imports every `.json` as a journal, even inside a folder, and hung on a manifest, which is why there isn't one). `GET /api/export/entries/:id` is one entry (a journal file holding it, plus its files; always a zip, because Day One imports only zips; `entryId` in `buildExport`, `entryInfo`/`entryId` params in the repo; in the entry menus). `?media=0` for JSON only, `?journalId=` for one journal (the Settings card has a journal picker; the journal edit dialog has Export…; both use `components/ExportControls.tsx`). Format reference: [docs/export-format.md](../../../../docs/export-format.md); update it whenever the output changes.
- `repo/export.ts` (`createRepos(...).export`) reads a user's live journals (archived included), entries, places, weather, tags, attached photos and attachments. `export/map.ts` is the pure mapping (the reverse of the importer: `toDayOneWeatherCode` in `packages/shared/src/weather.ts`, `![](photo:<id>)` back to `dayone-moment://`); `export/run.ts` hashes the originals (`hashMediaFiles`; the md5 names `photos/<md5>.<ext>`, and attachments go to `videos/`, `audios/`, `pdfs/` per `ATTACHMENT_LISTS`) and streams the zip with `yazl`; `routes/export.ts` is the one GET (it logs photos and attachments whose file is missing).
- Memory: only the journal list, the media rows (needed up front for hashing) and each journal's entry ids are read whole. Entries are read and stringified 200 at a time as the zip pulls a journal's file (`journalFile` in `run.ts` splices them into `journalShell`'s empty `entries`), so the output is byte-for-byte `JSON.stringify(file, null, 2)` while the journal's text is never all in memory (heap peak 34 MB on 11k entries). Keep it that way: don't collect a journal's entries into one array or string. The entry batch query uses `+user_id` so SQLite looks the ids up by key instead of scanning the user_id index.
- Imported entries keep the Day One keys Cairn has no column for from `source_raw`, except `richText` (stale once the text is edited) and any `cairn` keys (rewritten each export). Weather and places are written with only the values Cairn has, never defaulted.
- The importer reads the `cairn` extras back (`import/dayone/map.ts`: mood, dates to the ms, place label, weather source and condition, photo taken-at, attachment file name, journal name/colour/description/order/archived; a malformed extra is dropped, not an error). An entry is skipped if its Day One uuid or its Cairn id already exists, so re-imports and importing into the source account add nothing. Keep export and import in step: a new extra goes in `export/map.ts`, the schemas in `import/dayone/map.ts`, the doc, and the round-trip test.
- A journal of entries written in Cairn (places and weather included) imports into Day One cleanly. Photos, tags, all-day entries and multi-journal archives haven't been checked there specifically.
