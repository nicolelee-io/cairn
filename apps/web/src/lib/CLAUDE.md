# PWA, local store and sync

Design for offline writes: `docs/design/offline-writes-proposal.md`. User-facing list of what works offline: `docs/offline.md`; **update it whenever that changes**.

## PWA

- `public/manifest.webmanifest` is **generated** by `npm run theme -w @cairn/web` (don't hand-edit). Its `theme_color` is fixed into an installed Android app (WebAPK), so a change shows only after reinstalling or Chrome's WebAPK update. `index.html` links it with `crossorigin="use-credentials"` so Cloudflare Access doesn't reject the cookie-less fetch. The manifest is public and holds nothing private.
- **Service worker:** hand-written `public/sw.js` (no build step, no dependency), registered in production only (`lib/offlineCache.ts`). Navigations (except `/api/`) are network-first with the last app shell as fallback, and a 502/503/504/52x gateway reply counts as down; `/assets/*` and photo `display`/`thumb` are cache-first (originals never cached); `/api/auth/me`, `/api/journals` and `/api/entries*` GETs are network-first with the cache as fallback. Fallbacks carry `x-cairn-offline`. Writes are never touched; search, places, weather, export and backup aren't cached.
- Cache names: user data lives in `cairn-data-*` caches (API data, photos, the avatar, kept photos), deleted on sign-out and on any 401 (`clearOfflineData`). Keep the names in `sw.js` and `offlineCache.ts` in step, and put any new user-data cache under that prefix.
- Stale assets: `sw.js` never changes, so its `activate` doesn't run per deploy. The build writes `asset-list.json` (a plugin in `vite.config.ts`) and the page runs `pruneStaleAssets` on load.
- Updates: `sw.js` skips waiting and claims at once; what goes stale is the open page (an installed PWA never navigates). `lib/appVersion.ts` compares `__APP_SHA__` with `/api/health`'s `sha` on start, on focus and every 10 minutes, and `UpdateBanner` offers Reload, never reloading by itself. Dev builds never nag.
- To test: `npm run e2e -- offline` (`goOffline` in `e2e/helpers/offline.ts`), or by hand against a production build with the server stopped. DevTools "Offline" doesn't apply to the worker's own fetches.

## Local store and outbox

- `lib/localDb.ts`: one Dexie database per user (`cairn-<userId>`) with `journals`, `entries`, `photos`, `attachments` (records only; files are never kept), `outbox` and `meta`. `clearLocalCopy` (sign-out, any 401, "Clear data on this device") drops everything except the outbox, so queued writes survive a sign-out. Tests use `fake-indexeddb/auto`.
- `lib/outbox.ts`: when a write can't reach the server (`isUnreachable`: a failed fetch, a timeout, or 502/503/504), `sendOrQueue` (entries; also the reader's and menus' pin, star and move) or `sendOrQueueWrite` (everything else) parks the exact request and the UI carries on as if saved. Queued: entry create and edit, pin/star/move, journal create/edit/archive/order, account settings (`kind: 'me'`), and deletes. Uploads, the display name, username, password, picture and everything else need the server.
- Each row has a `kind` and a unique subject key (`outboxKey`: an entry id, `journal:<id>`, `journal-order`, `me`; a write and its delete share a key). `enqueue` merges by `mergeInto`: a later edit folds into a waiting one (first `baseRev` kept), an edit of a waiting create becomes part of it, a delete replaces a waiting edit or cancels a waiting create. A write queues behind one already waiting for the same key, so an older replay never overtakes a newer live write. An entry written in a journal whose create still waits queues behind it.
- **Overlays:** waiting writes are laid over every read that didn't come live from the server, so the UI shows them everywhere. `withPendingWrites` is the one overlay hook, registered into `api()` through `setOverlayHook` (`api.ts` can't import `outbox.ts`); `withPendingEdits` and `pendingCreateDetail` serve `fetchEntry` (an entry that exists only in the outbox has rev 0); `withPendingMe` lays waiting settings over every read of `me`, live ones included, so the 5-minute refresh can't flip a switch back. A journal with `rev: 0` hasn't reached the server.
- Replay: `flushOutbox` runs in `seq` order at start, on `online`, on tab visible, on Sync now and every 20s while something waits, under the Web Lock `cairn-outbox-replay` (`ifAvailable`, so a second tab skips). Unreachable or 401: stop and keep it. A 409 whose `current` already holds everything the edit sets (`matchesQueued`: our earlier send got through but its answer was lost) counts as done; a 404 on a delete counts as done. Any other refusal takes the item out, restores its draft snapshot to localStorage (unless a newer draft exists) and sets `review`.
- Undo of a delete that is still waiting takes it back out of the queue (`cancelQueuedDelete`, restoring the edit it replaced); once sent, Undo is a server restore.

## Offline rules

- **Everything either works offline or says it needs a connection.** Keyed on `useServerDown()`: a page or block that can't show anything without the server swaps in `NeedsConnection`; a page partly disabled offline gets an `OfflineBanner`; a control whose values still show is disabled with an `OfflineNote`; a menu action gets `disabled: 'Needs a connection'`. A new server-only control needs one of these; don't leave it to fail with a generic error.
- Sign out is disabled offline, and `useLogout` clears the device only once the server has ended the session (or answered 401); otherwise the cookie would sign straight back in on the next load.
- **Refusals and status:** offline is not an error and has no banner. `ServerBanner` is only for a refused replay (the one thing that needs action), an in-flow bar with Review and Dismiss. `lib/useSyncSummary.ts` computes the one state that matters, shown as `SyncStatus` in the nav and as `SyncIndicator` in `TopBar` below `large` while something needs attention.
- The QueryClient (`App.tsx`) uses `networkMode: 'always'` for queries and mutations. TanStack's default pauses them once the browser fires `offline`, which kept Save from ever reaching the outbox and reads from reaching the local copy. Keep it.
- Drafts stay in localStorage on purpose (SPEC section 3, Phase 7).

## Offline copies and sync

- Per device, chosen on the Offline & sync page (`/sync`, `pages/SyncPage.tsx`; shared logic in `lib/useOfflineControls.ts`) or a journal's "Keep on this device" switch; kept in the local database, never on the account. "Keep all journals" (`meta 'syncAll'`) adds new non-archived journals by itself. Sizes come from `GET /api/sync/estimate`.
- `lib/sync.ts`: `meta` holds `offline` (kept current), `backfill` (switched on, not downloaded yet), `cursor` and `syncedAt`. `syncNow` (Web Lock `cairn-sync`, never throws) pulls the feed from `cursor` for the `offline` journals, then downloads each `backfill` journal from 0. **Always pull incrementals before backfills** (a move between a synced and a new journal is then resolved by the later download). Each page is applied in one Dexie transaction. `reset: true` wipes the copy and downloads every kept journal again. It runs after the outbox replay (so our own saves are in the pull) at start, on `online`, on tab visible, every 5 minutes, on Sync now and after switching a journal on.
- Account settings aren't in the change feed, so `refreshMe` runs on the same triggers. It sets the cache only from a live answer (the worker's copy can predate a change made here) and never invalidates, since an errored `me` query shows `AuthGate`'s error screen.
- **Several open instances (a tab and the installed app):** both locks are `ifAvailable`, so a held lock must always end: the sync and replay requests use `api()`'s `timeoutMs` (30s) and photo downloads a 60s `AbortSignal`. **Any new background work that takes a Web Lock needs a timeout too.** A skipped `syncNow` retries after 15s; a finished one posts on `BroadcastChannel('cairn-sync')` so the other contexts refresh.
- **Local reads:** `lib/localRead.ts` answers `GET /entries/:id`, `/entries` (same cursor and archived rules), `/tags`, `/journals`, `/search` and `/search/matches` from the kept journals, in the server's exact shapes. `api()` asks it when the fetch fails, the gateway is down, or the service worker replied from cache (the local copy is fresher, except for the journal list). Network-first, not local-first: online you always see the server. The card rules live in `packages/shared/src/entryCard.ts`; keep any new card field in `entryCards()` (server) and `timeline()` here in step. Offline search (`lib/localSearch.ts`) ignores accents and case, has no stemming and always sorts newest first.
- **Kept photos:** after each pull `syncKeptPhotos` downloads `thumb` and `display` for every photo held into `cairn-data-offline-photos-v1` (header `x-cairn-keep` so the worker lets it through), which `sw.js` checks first. Originals are never kept. The name must match `KEPT_PHOTOS` in `sw.js`.
