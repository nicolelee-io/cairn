# Cairn todo and ideas

Features and ideas to build; finished ones move to [todo-completed.md](todo-completed.md). Bugs and known issues go in [tech-debt.md](tech-debt.md).

**Sections are about when, not how important.** New items go to **Inbox** with an estimate; triage moves them. **Next** is what gets picked up next (keep it to about 3-5 items), **Soon** is worth doing with no rush, **Later** is a real idea that is low value for its cost or waits on something, **Parked** is XL or strategic and not planned without a decision first. Small refinements to existing UI start with `Polish:`. Related ideas share one bullet rather than sitting apart.

**Estimates** (`_Est: model, time_`) are rough guesses from a quick look at the code, not a plan. Time is hands-on working time with Claude, including tests, the e2e run and doc updates; it is not calendar time. **Sonnet** = well-scoped work that follows existing patterns. **Opus** = cross-cutting, design-heavy or security/data-safety work, where a wrong first approach is costly. Sizes: XS under 30 min, S 1-2 h, M half a day, L 1-2 days, XL more.

## Parked

- Offline photo uploads: pick a photo with no connection, see it in the entry at once, and have it upload later. Today the entry's text queues but the photo has to be added again online. Scoped 2026-11-08, no migration. Pieces: `POST /api/photos` takes an optional client id and is safe to retry (the server generates the id today, despite SPEC 4d); the file waits in IndexedDB as a new outbox kind (Dexie version 3); `useUploads` queues when unreachable and inserts `photo:<id>` straight away; a downscaled copy in Cache Storage under `/api/photos/<id>/display` and `/thumb` lets the service worker show it with few changes at the render sites. Traps: a photo that lands after its entry never attaches (`syncEntryMedia` only attaches photos that exist at save, and cleanup tombstones the rest after 24h), so a save referencing a waiting photo must queue behind it, as `sendOrQueue` does for a waiting journal; a replay refused with a 415 (HEIC, a damaged file) must take the reference out of the waiting entry and say so, and sniffing the type at pick time catches HEIC early; the replay's 30s timeout is too short for a large photo on mobile, and a failing photo shouldn't hold up text behind it (a progress-based timeout, probably its own lane); `cairn-data-*` caches are deleted on sign-out and on a 401 while the outbox survives, so previews must be rebuilt from the stored file or cached elsewhere. Limits to accept: uploads run only while the app is open, a retry restarts the file, the only copy is on the device until it lands (browsers can evict storage, iOS most readily), and no server-read EXIF until then, so no "use the photo's location". Attachments stay online-only at first (up to 95 MB, and their files aren't kept offline). Update [offline.md](offline.md) when built. _Est: Opus, L for photos; about M more for attachments._

- HEIC/HEIF photo support: sharp's bundled libvips has no HEVC decoder, so HEIC uploads are refused and HEIC photos in a Day One import show no thumbnails. It can be done with a JavaScript decoder (`heic-decode` on WASM libheif, in a worker thread, plus `exifr` for the date and GPS) at the cost of memory on a small server and about 10 MB of dependencies. Parked until a real HEIC shows up in someone's data (iOS Safari already converts to JPEG on upload; a Day One import from an iPhone is the likely case). Findings, plan and risks in [heic-proposal.md](design/heic-proposal.md). _Est: Opus, M for upload and import; Sonnet, S to M for a catch-up job for already imported HEIC photos._

## Open Questions

- Can an MCP endpoint for an AI assistant sit behind Cloudflare Access? Access is the gate in front of the whole app, so a token-based route needs either its own Access service-token policy or a bypass for that one path, and each option changes what Access protects. It is the same Access question as the two-factor item, from the other side. Needs a short security write-up before any build; the answer unblocks both parked items. _Est: Opus, S (a decision and threat notes; the answer decides the feature's shape)._
