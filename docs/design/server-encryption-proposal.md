# Proposal: server-side encryption at rest

Status: proposal, not built, no decision made. Scoped 2026-11-08. It would replace the "Encryption at rest" item under Parked in [todo-and-ideas.md](../todo-and-ideas.md). Written after [e2e-encryption-proposal.md](e2e-encryption-proposal.md), which it replaces as the preferred direction.

## Summary

The goal is narrow: **an admin who is looking after the server should not see someone's photo or journal entry by accident**, for example by browsing the data volume, opening the database to debug something, or restoring a backup into a folder. Keeping out an attacker or a malicious admin is the job of the server's own security, not this feature. Users already have to trust whoever runs their server.

The server would encrypt photos, attachments and the database as it writes them and decrypt them as it reads them, using one key kept in the data volume. Devices and the app's features see no difference: search, import, export, photo processing and Insights all keep working as they do now.

Recommendations:

1. **Make it a server-wide setting** chosen by the admin. There is one database and one disk, so per-user encryption wouldn't add anything for this goal.
2. **Build it in two steps.** Media files first, since a stray photo thumbnail is the most likely accident, and that step needs no new dependency. The database second, since it brings in a new native dependency and changes the backup container.
3. **Keep the key in the data volume by default.** Nothing new to save or lose, and backups carry it. That means this does **not** protect a stolen disk, and the docs must say so.
4. **Keep it opt-in**, with a way back to plain files, because "SQLite + plain files on disk" is a stated goal in [SPEC.md](../../SPEC.md).

Rough size: about 4 to 6 working days for both steps, or about 2 for media alone.

## What it stops

| Situation | Today | Media step | Both steps |
|---|---|---|---|
| Browsing the volume and seeing photo thumbnails | Visible | **Stopped** | **Stopped** |
| Opening a photo, PDF or video from the volume by mistake | Visible | **Stopped** | **Stopped** |
| Opening `cairn.db` in a viewer, or running a query while debugging | Visible | Visible | **Stopped** |
| Searching the disk and hitting entry text in the database | Visible | Visible | **Stopped** |
| Restoring a backup into a folder and looking through it | Visible | Media stopped | **Stopped** |
| Pre-upgrade snapshots in `backups/` | Visible | Visible | **Stopped** |
| Copying the data folder to another drive, then browsing it | Visible | Media stopped | **Stopped** (unless the key file is opened too) |
| The app's admin pages | Already no route to content | No change | No change |
| Off-site backup repository | Already encrypted by restic | No change | No change |

What it doesn't stop:

- **Someone reading on purpose.** The key is next to the data, so anyone with access to the volume can decrypt it. That is accepted here: this is a closed curtain, not a lock.
- **A stolen disk or volume.** It includes the key. Disk encryption on the host (BitLocker, LUKS) is the answer, and the deployment docs should recommend it either way.
- **Plaintext that exists for a short time:** a zip waiting in `imports/` during an import (up to an hour, or the length of the run), and data in memory while it is being served.

The README and Settings must describe it in these terms. "Encrypted" alone would suggest more protection than this gives.

## Server-wide or per user?

**Server-wide.** Per-user encryption would be a natural fit if users needed protection from each other or from the admin's intent, but the goal is only to prevent accidents:

- There is one database file. Encrypting it for one user and not another means field-level encryption, which breaks search (see Alternatives).
- An admin browsing a volume benefits only if everything is covered, without having to know who opted in.
- One key is one thing to back up. Per-user keys would all sit in the same place, so they would add nothing here.

It is turned on with an environment variable rather than a switch in Settings, because the database can only be converted before the server opens it:

- `ENCRYPT_DATA=true`: encrypt, and keep new data encrypted.
- `ENCRYPT_DATA=false`: decrypt back to plain files.
- Unset: leave things as they are.

Settings > Server shows the state and the progress of the conversion, read-only. Users see nothing, and there are no client changes, service worker changes or new outbox behaviour.

## How it would work

### The key

- 32 random bytes generated by the server the first time it is turned on, in `/data/encryption.key` (owner-only permissions). It can't go in the database, since it unlocks the database.
- **The backup must include it**, or every restore fails. `backup.sh` adds it to the run, `restore.sh` writes it back, and `verify` fails if a snapshot of an encrypted server lacks it. The restic repository is itself encrypted, so storing it there is fine.
- There is one key for the server's life. The conversion can be run off and on again if it ever needs changing.
- A person copying the volume to a new machine brings the key along without thinking about it. Copying only `photos/` doesn't work, which the docs need to say (see the decrypt tool below).

### Media files

A new module, say `storage/sealedFile.ts`, becomes the only way to read and write these files.

- **Format:** a short header (a magic value, a version and a random salt), then AES-256-GCM chunks of 64 KiB. The per-file key comes from the server key and the salt through HKDF. Each chunk's number and a last-chunk flag are part of its nonce, so reordering or truncating a file is detected. This uses Node's built-in `crypto`, with no new dependency.
- **The file's path doesn't change.** It is encrypted in place, using a temp file and rename, so **there is no database migration or new column**. The header says whether a file is encrypted, so a server can hold both kinds while it converts, and turning it off works the same way.
- **Range requests:** `routes/attachments.ts` computes the plain size from the file size (the chunk layout is fixed) and reads only the chunks a range touches. Video seeking keeps working.
- **Temp files:** `attachments/upload.ts` and `storeAttachmentStream` stream to a `.tmp` file while hashing, so those are encrypted as they are written, after the type is sniffed. Photos are processed from memory buffers (`photos/pipeline.ts`), so they leave no plaintext temp file.

The places that touch these files, all found by searching the server code:

| File | Change |
|---|---|
| `photos/storage.ts` `storeOnce` | Writes sealed. `photos/quality.ts` `storeOriginal` goes through it |
| `routes/photos.ts` | Reads through the module; `Content-Length` becomes the plain size |
| `routes/attachments.ts` | Reads through the module, with Range and the plain size |
| `attachments/upload.ts` | Writes sealed, as above |
| `photos/avatar.ts`, `routes/avatar.ts` | Write and read through the module |
| `photos/compressExisting.ts` | Reads through the module, then writes as usual |
| `export/run.ts` | Hash and stream the decrypted bytes, at both of its read sites |

These need no change: `photos/gc.ts` (it deals in paths and dates), `storage/files.ts` (it reports on-disk sizes, which grow by about 0.03%), and ETags (based on the upload's hash).

**Converting existing files** works like the compress-existing job: one file at a time in the background, requiring a recent backup, resuming after a restart simply by skipping files that already have a header. Because it runs one file at a time, it needs almost no extra disk.

### The database

Replace `better-sqlite3` with [`better-sqlite3-multiple-ciphers`](https://github.com/m4heshd/better-sqlite3-multiple-ciphers) (MIT), a fork that adds encryption of every database page. Its author is also a `better-sqlite3` maintainer, and its current release tracks the same version (13.0.3) as ours.

- **What it covers:** the main file, the WAL, the search index and every snapshot, as one encrypted whole. FTS5 and all queries work as before, because encryption sits below SQLite's query layer. This is why whole-database encryption beats encrypting columns: there is no second copy of the text to deal with, and no query to rewrite.
- **In the code:** `openDb` in `db/index.ts` is the one place that opens the database, so it applies the key there. The CLIs (`import-journal.js`, `reset-password.js`, `make-admin.js`, `migrate-cli`) open through it and find the key in `DATA_DIR`. Build changes are the `--external` flags and the import.
- **Everyone gets the fork,** even with encryption off, because shipping both native modules makes no sense. It reads ordinary SQLite files normally. This is the main reason to do it second and to check it carefully.
- **Converting:** at startup, before migrations. Its docs say encrypting a plain database requires leaving WAL mode first, so: take a snapshot, switch to `DELETE` mode, set the key, return to WAL, run the integrity check. Exit if anything fails, like a failed migration. The plaintext snapshots in `backups/pre-migrate-*` are deleted once it succeeds, or they would stay readable.

### The backup container

This is the awkward part. The container's scripts use Alpine's `sqlite3` CLI for `.backup`, `integrity_check` and `verify`'s queries (`backup.sh`, `verify.sh`, `restore.sh`, `lib.sh`), and that CLI can't open an encrypted database.

| Option | Notes |
|---|---|
| **A small Node `sqlite3` stand-in using the same fork (recommended)** | It supports only the forms the scripts already use, which the test stub (`backup/test/stubs/sqlite3`) already lists. The scripts barely change. It adds Node to the image, and needs a musl build of the fork, which must be checked |
| Alpine's `sqlcipher` package | Only if it exists at the pinned release (not confirmed), and it would force the database into SQLCipher's format (`cipher='sqlcipher'`, `legacy=4`) |
| The app writes a nightly snapshot and the container only uploads it | No Node in the image, but `verify` and `restore` still have to read the database somehow, and it couples two schedules |

Since the container already mounts the volume, it finds the key with no configuration, and **a deployment's compose file doesn't change**. The manual checks in `backup/CLAUDE.md` must be re-run against real restic.

### Getting back out

A new `decrypt-data.js` CLI writes a plain copy of the database and files to a given folder, for someone moving away, repairing by hand, or using an outside SQLite tool. Export stays the everyday way to get data out and is unaffected. `ENCRYPT_DATA=false` undoes everything on the server itself.

## Effect on each feature

**Nothing users do changes.** Search with stemming and ranking, import from the app and the CLI, export, photo processing, weather, Insights, sync, offline copies and Manage users all work as they do now, because the server still has the plaintext while it works. The E2EE proposal's list of losses doesn't apply.

Things that change for admins:

- `sqlite3 cairn.db` and DB viewers stop working unless given the key. That is the point, but it slows down debugging. `decrypt-data.js` is the deliberate route.
- Restoring needs the key file, which the backup now carries.
- An older image can't read an encrypted database, and Watchtower doesn't roll back. So going back means `ENCRYPT_DATA=false` first, or restoring a backup from before it was turned on. A new image never encrypts unless asked, so ordinary updates aren't at risk.

## Server overhead

Measured for the media format, using Node's `crypto` on an ARM64 laptop (a throwaway script with the design above: 64 KiB chunks). Hardware without AES instructions would be several times slower; most x86 and ARM servers from the last decade have them.

| File | Decrypt per read | Size added |
|---|---|---|
| Thumbnail, 30 KB | 0.04 ms | 32 bytes |
| Display copy, 400 KB | 0.35 ms | 128 bytes |
| Photo, 5 MB | 3.5 ms | 1.2 KB (0.025%) |
| Video, 95 MB | 86 ms (about 1.1 GB/s) | 23 KB (0.024%) |
| Seeking in that video | 0.05 ms per chunk | |

**Not measured: the database.** The fork hasn't been installed or tested yet, so these numbers are from documentation, for a similar product rather than this library. SQLCipher's docs say [5 to 15% overhead isn't unusual](https://www.zetetic.net/sqlcipher/performance), and a [2011 note from its developers](https://groups.google.com/g/sqlcipher/c/BQBBVJ27kTM/m/qSCLquaZ8rgJ) suggests about 50% for full table scans, since each page must be decrypted. Cairn's single-entry lookups should be near the low end, and Insights and large exports near the high end. The first step of the work is measuring this.

| | Effect | Size |
|---|---|---|
| CPU serving media | Slightly up | Sub-millisecond for what the app mostly shows; well below the network and disk cost |
| CPU on photo upload | Slightly up | Milliseconds beside sharp's work |
| CPU on database queries | Up | Probably 5 to 15%, more on scans (unmeasured). Barely noticeable at this scale |
| RAM | About the same | Small chunk buffers. A somewhat larger SQLite page cache could offset scan costs, at a few MB |
| Disk, media | About +0.03% | 12 MB on 50 GB |
| Disk, database | About the same | Small per-page reservation |
| Converting 50 GB | One-time | About a minute of AES; the time goes on rewriting 50 GB of disk. Needs almost no spare disk, one file at a time |

Backups are the real cost:

- **One-time media growth.** The encrypted files are new data to restic, so the repository grows by the size of all the media, and the old copies stay until they age out (monthly snapshots for 12 months by default, [backup.md](../backup.md)). 50 GB of media means about 50 GB more off-site for up to a year, unless pruned. After the conversion, files go back to never changing once written, so nightly runs upload only what is new, as they do today.
- **A nightly database upload.** Today restic dedupes and compresses the database snapshot well (`data-dev`'s database gzips 4.7 times). Encrypted pages don't compress, and if a snapshot rewrites each page with a new nonce, nothing dedupes either, so the whole database uploads every night. That is the expected worst case and needs testing. At 10,000 entries (about 50 MB, scaling up from `data-dev`) and 23 retained snapshots, that's about 1.2 GB of repository. Small next to photos, and nothing for most users. If it ever matters, the container could stage a decrypted copy for restic, which encrypts it anyway.

**In short:** day-to-day overhead is low, and the only lasting cost is the one-time backup growth.

## Work

Sizes as in [todo-and-ideas.md](../todo-and-ideas.md). Opus-level throughout, as mistakes here can lose data.

| Step | What | Size |
|---|---|---|
| 1. Media | `sealedFile.ts`, the call sites above, Range, conversion both ways, status in Settings, the key file, adding it to backup and restore | L |
| 2. Database check | Before committing: does the fork install under `--ignore-scripts` on amd64, arm64 and musl? Measure queries at 20,000 entries. Check converting, `VACUUM INTO`, the backup API and how much restic dedupes. Go or no-go | S to M |
| 3. Database | The swap, `openDb`, startup conversion both ways, snapshots, CLIs | M to L |
| 4. Backup container | The `sqlite3` stand-in, script changes, re-checking against real restic | M |
| 5. Finish | `decrypt-data.js`, README, SPEC, deployment and backup docs, a full restore drill | S to M |

Step 1 is useful on its own and can ship alone. The media-only version keeps the backup container's `sqlite3` as it is, though it still has to include the key. A migration isn't needed, but it is a user-visible feature, so a minor version.

Tests that matter most:

- **A plaintext canary:** put a marker in an entry and a photo, then search the database, WAL, snapshots and data folder for its bytes. It must not appear.
- **Restore drill:** back up an encrypted server, restore to an empty folder with nothing else, start from it and read a photo, an attachment and a search result.
- **Interrupted conversion:** stop at each stage in both directions and check nothing is lost and it resumes.
- **Mixed media:** a server halfway through converting serves both kinds of file, including Range and export.
- **Corruption:** a damaged chunk gives an error rather than wrong bytes. A useful side effect: `verify full` could detect bit rot.

## Risks

- **Losing the key loses everything.** A backup without the key can't be restored. Mitigated by keeping it in the volume and the backup, and having `verify` check it. The risk is highest for someone who copies files by hand, so the docs need to be clear.
- **A native dependency that every install uses.** If the fork falls behind `better-sqlite3`, Cairn falls behind too. Switching back means decrypting first, and the fork reads plain files, so the way out exists.
- **A false sense of security.** People may read "encrypted" as "safe if my disk is stolen". The wording has to be exact.
- **Harder hand repairs.** Direct database access is a real help when something breaks on a small server, and it now takes an extra step.
- **Plaintext left behind after turning it on.** Old restic snapshots are still encrypted by restic, so that's fine for this goal, but a folder from an earlier restore, or an old copy of the volume, stays readable. Deleted plain files aren't overwritten on disk.

## Alternatives

- **End-to-end encryption** ([proposal](e2e-encryption-proposal.md)). Doesn't stop a malicious admin, who could change the app's code. It costs search, import and 10 to 15 days to keep out admins who were already trusted.
- **Encrypting only selected database columns.** Text would also need encrypting in the search index, so FTS5 wouldn't work on it; moods, dates and places are used in queries; and there is more code to get wrong. The whole-database option is simpler and covers more.
- **A key derived from each user's password.** Data would be closed while someone is signed out, but background work (weather, cleanup, exports, conversion) couldn't reach it, and a password reset by an admin would lose the data. All that goes well beyond preventing accidents.
- **An external key** (an environment variable instead of the file). It would protect a stolen volume, but brings the lost-key risk back, and the backup can no longer carry the key. It is easy to add later if someone needs it, because the format wouldn't change.
- **Simply hiding files:** no extensions and no thumbnails, with no encryption. Cheap, and a file manager would stop previewing them, but anything that opens the file by its contents still shows it, and it does nothing for the database. Once a read and write layer is needed anyway, real encryption costs about the same and also detects corruption.
- **Doing nothing, plus advice.** "Don't browse the volume" costs nothing and works for a careful admin. The accident this proposal is about happens to careful admins, though.

## Open questions

1. **Is the media step enough?** It stops the likely accident (a photo on screen) for about 2 days of work and no new dependency. The database step costs another 2 to 4 days, the fork and the backup changes, and stops someone seeing text while debugging, which is a less likely accident, since opening the database is already a deliberate act. Recommended: ship media, then decide with real use.
2. **Opt-in or on by default for new servers?** Recommended: opt-in for now. It could become the default for new installs once it has run for a while.
3. **Should the conversion prune old backups?** Recommended no: old snapshots are protected by restic, and pruning removes history for everyone. The docs give the admin the pruning command in case the extra storage matters.
