## Backup

- Optional sidecar image from `backup/` (Alpine, tag pinned to the release whose restic the scripts were checked against: restic, rclone, sqlite, bash scripts), compose profile `backup`, all config in `.env.backup` (git- and docker-ignored; not the app's `.env`). CI builds `ghcr.io/<owner>/cairn-backup`. Full guide: [docs/backup.md](../docs/backup.md); keep it in step with the scripts.
- `backup/cairn-backup` is the entry point (`run` = daily at `BACKUP_TIME`, `init`, `now`, `verify [full]`, `restore <empty dir> [id]`, `snapshots`, `restic ...`); `lib.sh`, `backup.sh`, `verify.sh`, `restore.sh` hold the logic. A run: `sqlite3 .backup` of the live DB into a stage dir, `integrity_check` on the copy, `restic backup` of that copy plus the `MEDIA_DIRS` in `lib.sh` (`/data/photos` and `/data/attachments`; a new file folder in the data dir must be added there) (fixed host `cairn`, tag `cairn`), `forget --prune` (7 daily, 4 weekly, 12 monthly), `check` (plus 1% of the data). `verify` restores only the DB and compares the live photo and attachment rows against `restic ls` (a DB from before migration 0010 has no `attachment` table: `has_attachments_table`); `verify full` reads all data. `restore` writes `cairn.db`, `photos/` and `attachments/` into an empty dir and refuses the live data dir.
- The sidecar mounts the same named volume (`cairn_data:/data`, not a bind mount: the DB's -shm must be shared properly) and runs as uid 1000 like the app. It writes `backups/backup-status.json` (`lastRun`, `lastSuccess`, `lastVerify`; built by hand, no jq), which `backup/status.ts` reads for `GET /api/backup/status` and the Settings card (`none` / `ok` / `failing` / `stale` after 36h). The status holds times, a snapshot id and error text only, never the repository address or credentials. A missing or malformed file is `none`, never an error. The format is pinned by `backup/test/fixtures/status-*.json`: `run.sh` checks the scripts write that shape (`same_shape`: same keys and JSON types) and `status.test.ts` reads the same files, so change a fixture first when the fields change.
- `backup/test/run.sh` (run in CI) tests the scripts against stand-ins for restic, sqlite3 and curl in `backup/test/stubs`. They don't test restic itself; the flags used (`ls --recursive`, `restore --include`, the `--json` summary) were checked against restic 0.18.1 (Alpine 3.24's, the pinned tag) by hand; bump the tag only together with that re-check. After changing the scripts, re-check against the real image: `docker build ./backup`, then `init`/`now`/`verify`/`restore` with a local repository volume (chown it to uid 1000).
- A deployment that pulls the images has its own compose file with its own `backup` service (external `cairn_data`, its own `.env.backup`), so a change to the backup service here has to be made there too (ask first; it is config). Where the maintainer's is: `CLAUDE.local.md`, when present. The Watchtower pre-update hook was left out: nightly backups plus the pre-migration snapshot cover the cases it would.
